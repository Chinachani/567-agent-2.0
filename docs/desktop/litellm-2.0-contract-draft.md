# LiteLLM 2.0 双端与后端接口合同草案

> 2026-10-15：已在独立 2.0 仓库开始实施，源码基线同步至 v1.2.13（`ed86395fb`）；以下保留最初审查基线，当前完成项与未完成项以[实施进度](litellm-2.0-progress.md)为准。

日期：2026-10-13。状态：候选合同，尚未由业务后端实现或发布。与[开工计划](litellm-2.0-preflight.md)和[工程补充计划](litellm-2.0-engineering-plan.md)配合使用。

## 服务边界

| 服务 | 地址与认证 | 拥有的规则 |
| --- | --- | --- |
| 独立业务服务 | `API567_SERVICE_URL`，业务 Access/Refresh 会话 | 账号、套餐、按量账本、订单、模型目录、调用授权与对账 |
| LiteLLM 网关 | `API567_GATEWAY_URL`，受限模型凭证 | 模型协议、上游路由、网关权限和限速、调用记录 |
| 用户自定义供应商 | 用户配置的地址、协议与 Key | 供应商自己的认证、模型、速率和收费；不访问官方业务账本 |
| 外部工具服务 | 明确服务基址和工具授权 | MCP/能力发布的实际服务权限，不能使用模型 Key 冒充业务 Token |

业务 API 和网关基址都允许合法部署路径前缀。以下路径展示完整逻辑端点；实现中由统一解析器组合基址和协议路径，不同时把 `/api/v2` 或 `/v1` 拼两次。原生 Responses、Anthropic 和自定义协议的端点映射分别声明。

## 业务端点候选

| 方法和路径 | 返回或作用 |
| --- | --- |
| `POST /api/v2/auth/login` | 建立业务账号会话；具体账号密码/验证码方式另行确定 |
| `POST /api/v2/auth/refresh` | 轮换业务会话，单飞刷新；请求结果未知时不能直接清空或复用已撤销令牌 |
| `POST /api/v2/auth/logout` | 撤销业务会话与官方授权；不删除自定义 Key 或本地会话 |
| `GET /api/v2/account/status` | 账号状态、套餐周期与额度、速率、按量账户、兜底偏好和修订号 |
| `PUT /api/v2/account/fallback` | 更新自动兜底与消费上限，返回生效偏好和修订号；冲突有明确反馈 |
| `GET /api/v2/models/catalog` | 当前用户官方可用模型、订阅/按量权限和富元数据，不含密钥 |
| `POST /api/v2/model-access` | 获得受限模型访问能力；凭证留在平台秘密存储，不进 Renderer 快照 |
| `GET /api/v2/requests/{operationId}` | 查询该用户操作的执行、取消和结算状态 |
| `POST /api/v2/requests/{operationId}/cancel` | 记录取消意图，返回当前状态；不是立即退款保证 |

调用前的套餐预留采用业务授权端点或网关策略之一，由服务端固定合同，不能两边独立预留两次。支付、充值和订阅订单端点待业务实现与支付方式确定后补齐，不能接回旧 NewAPI 账户充值 API。

### 原生 cloud 的兼容映射

以上 `/api/v2` 是候选公开路由，不要求重写现有 cloud 注册体系。当前旧 cloud 使用配置基址下的以下逻辑端点，服务端可提供兼容端点，或由 cloud 内部的版本适配器映射到新合同：

| 旧逻辑端点 | 当前响应约定 | 新合同的职责 |
| --- | --- | --- |
| `/auth/refresh` | `code: 0` 与 `data.access_token/refresh_token`；401 返回统一 unauthorized | 业务会话轮换、明确失效原因、未知结果恢复；与新登录/注销共享账号代次 |
| `/subscription/me` | `data` 中的 active、旧 go_enabled 与周期 windows | 标准订阅、按量账户、兜底偏好与修订号；不能把旧字段当作新权益规则 |
| `/providers/models.json` | `data.providers` 产品模型目录 | 版本化富目录、来源和协议能力、通道授权；不在目录中发布密钥 |

服务地址前缀、响应 envelope 和字段映射集中处理，不在 Renderer、Runtime 和手机各自猜测。保留现有刷新单飞、Bridge 与热重载接口的可复用机制；官方模型请求与旧业务 JSON 网关分别处理。原生 cloud 没有完整 2.0 后端，本合同也不恢复旧 OAuth/网页跳转。

刷新错误以受控 code 表示失效、过期、撤销或暂时性故障；旧 40105/40106/40107 可映射，但当前日志字符串不是已实现的结构化合同。模型请求 401、套餐 403/429 与刷新认证失效分别处理；刷新结果只允许提交到发起时的账号代次，注销后的迟到成功不能重新登录。

## 账号、权益与金额类型

- 每个响应明确 `schemaVersion`、状态修订号和 `asOf`；时间使用带时区的 ISO 8601。套餐状态与过期时间不是通过余额大小推断。
- `subscription` 包含有效状态、档位、周期开始/结束、额度单位、总量/已用/剩余、模型授权与 RPM/TPM/并发限制。具体额度单位和周期由服务端配置。
- `payAsYouGo` 包含可用状态、余额、按量价格表版本、可用模型和速率限制。它与独立 NewAPI 的账户余额没有隐式兑换关系。
- `fallback` 包含是否开启、消费上限的金额和周期、当前用量与修订号，默认关闭。仅“套餐额度不足”允许按预先同意的规则切换，其他错误不自动切换。
- 金额不用 JSON 浮点数。候选 `Money` 为 `currency`、`minorUnits`（十进制整数字符串）、`scale`；每次核销包含价格表版本、舍入规则和明确单位。报价可用固定精度十进制字符串，不能把原 quota 直接按 500000 折算美元。
- 用量和金额分开表示。客户端若缺少实际 usage，显示未提供或估算，不把缺失值设为零并参与结算。

订阅与按量的模型范围和速率独立下发。自动兜底是否允许套餐之外的模型或更高限速尚未确认，客户端不自行开放。

## 官方模型目录

目录至少声明：

- `catalogVersion`、`revision`、官方网关标识和模型来源。
- `providerId`、稳定模型 ID、显示名与公开 gateway alias；上游部署 ID 属于网关内部信息。
- API 协议、输入模态、上下文窗口、输出 Token 上限、推理参数与默认等级。
- 工具调用、结构化输出、流式 usage、原生文件输入、图片生成/编辑和视频任务能力。
- 各能力使用的端点与受支持参数，如尺寸、参考图数量、`response_format` 和模型特定限制。
- 用户在订阅与按量两种方式下的模型授权，以及价格引用；价格和能力不能仅靠模型名字推断。

未知能力不可默认为支持。官方条目不得提供让客户端绕过 LiteLLM 的 `upstreamBaseUrl`；用户自定义条目仍使用其自身配置。目录缓存和不可用历史条目允许只读呈现，发送前重新执行当前权限检查。

### 推理协议要求

- API 协议和推理合同分别声明，不能因接入 LiteLLM 就一律改为 `openai-completions`。仅声明该客户端和网关版本共同支持的组合，所有官方协议仍通过受限 LiteLLM 路由。
- 出站推理参数、响应字段、签名/不透明块的格式及后续工具结果回放要求分开定义。客户端 `thinkingFormat` 的选择由已验证的出站合同决定，不按上游品牌推断。
- Anthropic 扩展推理等需要 `thinking_blocks` 的组合必须保留必要原始信息；不能只保存显示文本就宣称多轮工具兼容。能力不足时给明确限制，不静默关闭推理。
- `drop_params` 和 `modify_params` 不构成完整推理保证。合同规定的关键参数不能在用户无感知时丢弃；明确允许的兼容转换须有版本和行为验证。

## 模型调用与请求身份

| 标识 | 生命周期 |
| --- | --- |
| `turnId` | 一次用户回合的关联范围，不作为所有模型调用共用的收费幂等键 |
| `operationId` | 一个真实模型或媒体操作；自动传输重试保持不变，工具后续、预测、命名、上下文压缩和新的用户尝试各用新值 |
| `attemptId` | 网络传输尝试，关联同一 operationId；不能导致新的预留或收费 |
| 网关/上游 ID | 由网关或供应商产生，与 operationId 在服务端绑定并用于核对 |

客户端使用 UUID 等可全局区分的标识，服务器再绑定账号、调用用途、模型和请求摘要。`X-Request-Id` 仅用于相关性；若使用 `Idempotency-Key` 或 metadata，需以本项目服务端确实实现的行为为准，不能依赖未验证的 LiteLLM 或上游去重。

计费来源由服务端确定。官方请求使用受限模型凭证并经过权威计费策略；自定义请求不创建官方账本记录。Key 的用户、模型范围、有效期和访问受众不能由客户端 headers 或 metadata 扩大。

服务端响应或操作状态应能返回实际 `billingMode`、价格版本、真实 usage 状态和最终金额；客户端明确展示订阅额度或按量计费。不要在上游还未确认之前把预留金额显示为最终扣款。

## 取消、重试与结算状态

候选状态：`accepted → reserved → executing → completed/failed/cancel_requested → settling → settled`。未知上游结果进入 `reconciling`，重复请求读取已有操作状态。

- 同一 operationId 的重复提交不产生第二次上游调用或账本核销；ID 对应的请求摘要变化返回冲突。
- 用户主动发起新的尝试使用新操作，并关联此前操作；结果未知时界面提示待核对，不以“网络超时”宣称未扣费。
- 取消响应包含是否受理和当前状态。已产生的真实用量仍结算，仅释放未使用的预留。
- 请求中止、客户端崩溃或断网后，服务器继续完成取消、租约回收与对账。客户端再次打开可查询最终状态。
- 生图与视频存在异步任务，提交、轮询、下载共享任务身份；轮询和下载不是新的收费生成操作。

## 流式输出与 usage

- 对官方 Chat Completions 开启 `stream_options.include_usage=true`；不支持该参数的自定义端点使用兼容设置。其他协议按原生合同处理。
- 纯 usage chunk 可有 `choices: []`。先到的 `finish_reason`、最后的 usage 与 `[DONE]` 是不同信号；更新用量不能重复结束回合或丢弃已完成正文。
- 合法 EOF 不因缺少 usage 被报为正文截断。保持现有异常 EOF、损坏 JSON、分片工具参数和资源上限的测试。
- 业务账本以服务端记录核销，客户端 usage 主要用于反馈与核对；供应商没报告或网关作估算时保留来源和准确性状态。

LiteLLM 末尾 usage 形态与可选的网关自动包含设置见[官方说明](https://docs.litellm.ai/docs/completion/usage)。这不是所有自定义供应商必然遵循的行为。

## 错误与权限

统一错误对象包含业务 `code`、可展示信息、是否可重试、operationId 和必要的限速重试时间。错误信息不携带 Token、Cookie 或完整隐私请求。

至少区分：账号需要登录、会话过期、模型未授权、模型不可用、套餐额度不足、按量余额不足、消费上限、限速、计费状态待核对、参数不兼容和媒体保存失败。HTTP 403 或 429 单独不能证明应该注销或开启付费兜底。

## 凭证与模型历史兼容

- 工具凭证与模型 Key 使用不同文件/接口和权限受众；旧 `auth.json` 的读取适配明确版本与 API 前缀，不根据任意字符串自动更换目标服务。
- 一次性旧配置迁移记录明确的用户选择、provider 别名和事务状态，使用凭证保险库接口。`source: managed` 是待设计的来源合同，不是当前旧文件必有字段。
- 历史消息引用保持原样；无法解析的模型显示已停用，用户选择新通道后才开始新的调用。不能把自动挑选另一付费 provider 当作读取旧记录的必要条件。

本合同在客户端、业务服务与网关之间共同验收后再固定版本；当前不存在生产接口承诺或已实现的收费保证。
